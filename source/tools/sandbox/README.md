# Изоляция запусков APF — стратегия и уровни

> Создано после инцидента 2026-07-28: прогон `go test ./internal/engine/` включил системный
> HTTP-прокси `127.0.0.1:1081`, где sing-box не слушал, и связь пропала на всей машине.

## Почему обычного запуска недостаточно

APF по устройству меняет **глобальное** состояние машины. Список того, что он трогает, и чем
это грозит:

| Что меняет | Где в коде | Цена ошибки |
|---|---|---|
| Политика Windows Firewall (`blockoutbound`) | `internal/killswitch` | Обрыв всего исходящего трафика |
| WFP-фильтры (FWPM) | `internal/killswitch/wfp_windows.go` | То же, но переживает смерть процесса |
| **Системный HTTP-прокси (HKCU)** | `internal/sysproxy` | **Обрыв WinINET/WinHTTP. Прав admin НЕ требует** |
| Таблица политик префиксов IPv6 | `internal/leakguard` (устранено) | Ломает выбор адреса назначения, **не откатывается** |
| DNS адаптеров | `internal/killswitch/reset.go` | Отказ резолвинга |
| TUN-интерфейс `apf0`, маршруты | sing-box | Перехват всего трафика |

Ключевой урок: **запись в HKCU не требует администратора**, поэтому «мы же запускаем без прав»
не является защитой. Именно этот путь и обрубил связь.

## Уровень 0 — барьер `hostguard` (работает всегда, ничего включать не надо)

Пакет `internal/hostguard` — единая точка решения «можно ли трогать ОС».
Каждый мутатор обязан начинаться с `hostguard.Allow("имя.операции")`.

* Под `go test` барьер **взведён** → операция становится no-op и попадает в счётчик.
* Снять барьер можно только переменной `APF_ALLOW_HOST_MUTATION=i-know-this-is-an-isolated-vm`
  — значение намеренно длинное, чтобы его нельзя было выставить случайно.

**Инвариант: `go test ./...` не изменяет ни одного параметра ОС.**

Доказывается двумя способами:
1. `internal/sysproxy/hostguard_windows_test.go` → `TestMain` снимает реальные значения реестра
   до и после **всего** прогона пакета и роняет тест при расхождении.
2. `tools/apf_host_snapshot.ps1 -Run "..."` — внешний снимок 8 групп параметров до/после.

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File tools\apf_host_snapshot.ps1 -Run "go test ./internal/..."
```
Код возврата `2` = хост изменился (дефект). `0` = чисто.

**Чего уровень 0 НЕ даёт:** он защищает только от тестов. Настоящий запуск приложения
(`apf.exe`, `apf-tray.exe`, служба) барьер не проходит — он и **должен** менять систему.
Для него нужны уровни ниже.

---

## Уровень 1 — Docker / WSL2 (доступен на этой машине **уже сейчас**)

Контейнер имеет собственный сетевой namespace: что бы iptables ни сделали внутри, хост
физически недосягаем.

```bash
docker run --rm -it --cap-add NET_ADMIN --cap-add NET_RAW \
  -v <workspace>:/src:ro \
  golang:1.26 bash
```

**Что проверяет:** `linuxKS` (цепочка `APF_KS`, `-o tun`), sing-box в TUN-режиме, логику
подключения, всё платформо-независимое ядро.

**Что НЕ проверяет (важно!):** ничего из Windows-пути — ни netsh, ни WFP, ни named pipe,
ни UAC, ни службу `apf-svc`. То есть **B-0402.3 и B-0402.4 здесь не верифицируются.**

## Уровень 2 — Windows Sandbox (НА ЭТОЙ МАШИНЕ НЕДОСТУПЕН, см. вердикт)

> **Вердикт 2026-08-04: включить нельзя.** Проверено дважды (29.07 и 04.08), на свежезагруженной
> машине, обоими путями — `Enable-WindowsOptionalFeature` и `dism.exe`. Оба падают одинаково:
> `CBS HRESULT=0x80188306`, «Failed finalizing changes».
>
> Причина установлена (`tools\sandbox\sandbox_diagnosis.txt`):
> * `DISM /Online /Cleanup-Image /CheckHealth` → **«Повреждение хранилища компонентов не обнаружено»**;
> * при этом `Get-WindowsPackage -Online` → **ни одного пакета `Containers-DisposableClientVM`**;
> * `VirtualMachinePlatform` = Enabled, политик, запрещающих песочницу, нет.
>
> То есть хранилище исправно, но полезной нагрузки компонента в нём просто нет — образ урезан.
> `RestoreHealth`/`sfc` тут не помогут: чинить нечего, нужен **источник пакета**.
> Лечится установочным образом Windows 11 той же сборки:
> ```
> DISM /Online /Enable-Feature /FeatureName:Containers-DisposableClientVM /All ^
>      /Source:wim:<буква>:\sources\install.wim:1 /LimitAccess
> ```
> Тот же ISO нужен и для уровня 3, поэтому отдельной ценности восстановление песочницы не имеет:
> **уровень 3 покрывает всё, что дал бы уровень 2, и сверх того.**

Диагностика (только чтение, ничего не меняет):
```powershell
tools\sandbox\diagnose_sandbox.ps1
```

Если песочница всё же будет восстановлена — одноразовая ВМ с Windows: свой сетевой стек, свой
реестр, свой фаервол. Учётка внутри — администратор, поэтому доступны admin-путь KS, WFP,
установка службы, UAC.

```powershell
# один раз, из консоли «от имени администратора»:
tools\sandbox\enable_windows_sandbox.ps1
# перезагрузка, затем:
explorer.exe tools\sandbox\apf_sandbox.wsb
```

`apf_sandbox.wsb` пробрасывает только для чтения исходники, Go и MinGW; `sandbox_bootstrap.ps1`
копирует дерево в записываемый `C:\work`, снимает барьер `hostguard`, делает базовый снимок сети
и собирает проект.

**Что проверяет:** почти весь Windows-путь — netsh Kill Switch, WFP-фильтры, системный прокси,
TG-1 (100 циклов Enable/Disable), позитивный тест VPN-режима.

**Ограничения, о которых надо знать заранее:**
* Состояние не переживает закрытие окна — сценарии «перезагрузка с активным KS» и
  crash-recovery через reboot здесь не воспроизвести.
* Установка службы Windows работает, но проверить `DelayedAutoStart` при старте ОС — нет.
* Вложенная виртуализация ограничена; отдельного «второго» сетевого адаптера не будет.

## Уровень 3 — Hyper-V ВМ с Windows (ШТАТНЫЙ СТЕНД проекта)

Проверено 2026-08-04: `Microsoft-Hyper-V-All` = Enabled, служба `vmms` работает,
коммутаторы `Default Switch` и `WSL (Hyper-V firewall)` на месте, модуль `Get-VM` доступен.
**Готово к работе, включать нечего.**

Единственный уровень, где проверяются:
* поведение службы `apf-svc` при **старте и перезагрузке** ОС;
* crash-recovery после жёсткого выключения питания (`-Action Kill`);
* персистентность WFP-фильтров и sentinel-маркера между сессиями;
* снимки — откат к чистому состоянию за секунды (обязательны для 100 циклов TG-1);
* **два пользовательских сеанса** (R-5.2): в песочнице пользователь ровно один,
  поэтому проверка авторизации канала по владельцу консоли там невыполнима в принципе.

Это обязательный уровень для финальной приёмки Gate A.

Оснастка — `tools\sandbox\hyperv_stand.ps1` (управляет только ВМ; APF не запускает никогда):

```powershell
.\tools\sandbox\hyperv_stand.ps1 -Action Check                       # состояние, ничего не меняет
.\tools\sandbox\hyperv_stand.ps1 -Action Build                       # бинарники в source\bin (без прав админа)
.\tools\sandbox\hyperv_stand.ps1 -Action Create -IsoPath "<Win11.iso>"
.\tools\sandbox\hyperv_stand.ps1 -Action Start                       # установить Windows вручную
.\tools\sandbox\hyperv_stand.ps1 -Action Provision                   # исходники+бинарники в гостя по VMBus
.\tools\sandbox\hyperv_stand.ps1 -Action Checkpoint                  # снимок "clean" ДО запуска APF
```

`-Action Build` собирает `apf`, `apf-svc`, `apf-tray`, `apf-wfpcheck` в `source\bin`
(проверено 2026-08-04: все четыре собираются, CGO включён, gcc — `D:\winlibs\mingw64\bin`).

Внутри гостя — `C:\apf-drop\hyperv_bootstrap.ps1`: распаковывает исходники, снимает барьер
`hostguard`, делает снимок сети, собирает проект. Он защищён тройной проверкой изоляции
(модель `Virtual Machine` + маркер `C:\APF-STAND.marker` + чёрный список имён рабочих машин),
потому что снимает единственный барьер, удерживающий APF от изменения ОС.

Между прогонами:
```powershell
.\tools\sandbox\hyperv_stand.ps1 -Action Reset   # откат к снимку "clean"
.\tools\sandbox\hyperv_stand.ps1 -Action Kill    # снять питание — вход в сценарий crash-recovery
```

Что нужно от человека: **установочный образ Windows 11** (ISO) и ручная установка ОС в госте.
Всё остальное автоматизировано. Файлы ВМ создаются в `D:\APF-Stand` — временно вне папки
проекта: по правилу проекта всё должно лежать внутри папки проекта (кроме кэша самого Claude),
но перенести уже существующую ~35 ГБ ВМ через `Move-VMStorage` не вышло 2026-08-31 — не хватило
свободного места на D: (нужно ~35 ГБ, было ~10.7-29.7 ГБ). Остальные кэши сборки (Go/Gradle)
уже перенесены в `<папка проекта>\APF-Stand\`, ВМ переедет туда же, когда появится место —
тогда же обновится `-StandRoot` по умолчанию в `hyperv_stand.ps1`.

Передача файлов идёт по VMBus (`Copy-VMFile`), а не по сети: обрыв связи внутри гостя —
ожидаемый результат тестов Kill Switch — не мешает доставке и не требует общей папки с хостом.

Go в госте нужен только для `go test`. Для рантайм-приёмки достаточно бинарников,
собранных на хосте (сборка хост не меняет и правилом не запрещена).

## Правило выбора уровня

| Задача | Уровень |
|---|---|
| `go test`, сборка, статический анализ | **0** — прямо на хосте, барьер держит |
| Логика подключения, Linux Kill Switch | **1** — Docker |
| Windows Kill Switch, WFP, TG-1, прокси | ~~**2** — Windows Sandbox~~ → **3** (уровень 2 недоступен) |
| Служба, перезагрузки, crash-recovery, два сеанса | **3** — Hyper-V ВМ |

**Запрещено:** запускать `apf.exe` / `apf-tray.exe` / `apf-svc` на рабочей машине для проверки
Kill Switch. Для этого есть уровни 2 и 3.

## Если связь всё-таки пропала

1. `tools\apf_emergency_restore.bat` — эскалация восстановления (фаервол → DNS → полный сброс).
2. `tools\apf_host_snapshot.ps1 -Diff before,after` — что именно изменилось.
3. Ручной минимум, если не работает ничего:
   ```
   netsh advfirewall set allprofiles firewallpolicy blockinbound,allowoutbound
   reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable /t REG_DWORD /d 0 /f
   ```
